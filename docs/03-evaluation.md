# 对照组与结果判读

基准的建设、打分命令和 L3 执行、L4 人工评审的接入见 [05-benchmark.md](05-benchmark.md)。本页讲"跟谁比、在哪个集合上比、结果怎么读"。

## 1 三件事分开说

| 结论 | 证据 | 不能推出 |
| --- | --- | --- |
| 训练完成 | `status.json` 为 `training_completed`，`adapter_max_abs_change > 0` | 效果变好 |
| 加载成功 | 重新启动进程加载适配器并在基准上生成 | 效果变好 |
| 业务改善 | 冻结基准上 B1 相对 B0 的逐任务对照，含执行和人工评审 | 对所有业务都改善 |

loss 下降、静态指标（L0–L2.5）改善都只是中间证据。

## 2 对照组

| 组 | 模型与流程 | 怎么得到 | 用途 |
| --- | --- | --- | --- |
| A | 团队现有工作流（WorkBuddy、所用模型、Skill、多轮修复） | 把每个实例的输出存为 `<instance_id>.txt`，`scripts/bench/import_run.py --arm A --note "<模型/Skill 版本/重试次数>"` | 业务参照：值不值得替换 |
| B0 | 开源模型，未训练，相同提示和资料 | `run_generate.py`，不带 `--adapter` | 训练前的起点 |
| B1 | 同一模型，训练后，相同提示和资料 | `run_generate.py --adapter runs/train/E00X` | 训练后的结果 |

- **B1 对 B0** 才是训练效果的归因。两者的基准版本、模型 lock、`max_new_tokens`、`generation` 必须一致；`compare.py` 会拒绝基准、规则、评分器版本不同的运行。
- **B1 对 A** 是系统选型。A 往往用更大的模型、更长的提示、工具和重试；把这些条件写进 `--note`，不要把全部差异归因于训练。
- A 的输出要原样导入；人工修改记在 `review.csv` 的 `repair_minutes`，不要改输出文件。
- 同一基准版本、同一模型、同一生成设置下，B0 只需生成一次，后续实验复用（`compare.py` 的第一个参数放它）。

## 3 成本也是结果

除了质量，单列：输入 token 数（B 的提示通常比 A 短得多）、输出 token、生成耗时（`records.json`）、人工修复分钟数（`review.csv`）、数据整理与训练耗时。"质量不变但提示更短、修复时间更少"也是有效结论。

## 4 dev 与 test 的使用纪律

| split | 用途 | 规则 |
| --- | --- | --- |
| dev | 每轮迭代、选配置、看失败案例 | 可以反复看；据此修改训练数据要在实验记录里写明 |
| test | 方案定稿后的最终判断 | 每个定稿方案只跑一次；看了结果再回去改方案，test 就变成了 dev，需要补新实例另组 test |
| holdout_domain | 整个领域都不进训练池 | 检验跨领域迁移，定稿后与 test 一起跑 |
| fresh | 训练之后才写出来的新脚本 | 定期补充，检验时效和污染 |

日常命令只写 `--splits dev`。在实验记录里登记 test 的每一次运行。基准 v0.x 只有十几个实例，全部放 dev；规模扩大到能拆出 test（每个 split 至少几十个实例）时再拆。

不要用 dev 的失败案例直接"改题"：基准实例冻结后不能改。发现实例本身有错（oracle 写错、gold 有误），在 pool 中修正后发布新版本，旧结果不与新版本比较。

## 5 怎么读对比报告

`compare.py` 输出四部分：各层指标（计数/分母）、按标签切片、相对第一个运行的配对变化（improved / regressed）、逐任务结果与失败原因。

1. **先看 generated 和 L0**。截断、围栏、语法错误多，后面各层都没有意义，先解决格式或生成预算。
2. **看配对变化，不看比例差**。"B1 改善 5 个、退步 1 个"比"通过率 40% → 52%"更可靠。只差一两个任务时视为噪声，可以换 `seed` 训练一次确认。
3. **看切片**：按 `flow`（正常流/异常流）、`domain`、`difficulty` 看是哪类任务在变。总体不变但异常流变好、正常流变差，是两个不同的结论。
4. **看失败原因的分布**：`must_call missing` 多说明没调用关键接口；`expect ... value_only` 说明断言了值但没断言到正确对象；`ungrounded call` 是编造；`copied reference identity` 是照抄。
5. **用 L3、L4 校正 L2.5**。静态判定通过但执行失败、或评审认为没有按剧本实现的，以 L3、L4 为准；两者经常不一致的实例，说明它的 oracle 写得不够好，记下来在下个版本改进。

规模：dev 只有十几个实例时只做逐任务案例分析，报原始计数。至少几十个、覆盖多个领域后才解读比例。实例数为 50 时，两种方案通过率要相差约 15–20 个百分点以上才较可能区分开。

## 6 写结论

报告模板：`templates/report.md`。可以是这样的结论：

- 训练减少了某类错误（如编造接口、Markdown 围栏），但没有提高 oracle 通过数。
- 对正常流有效，对异常流退步。
- 质量持平，但提示 token 和修复时间下降。
- 训练没有带来可确认的改善。

保留不利结果和失败案例。改善只出现在与训练样本相似的任务上时，先检查泄漏（`check_leakage.py` 的近重复提示）、重复数据和任务难度，不要扩大结论。
