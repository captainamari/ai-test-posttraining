# 基准设计依据与实现状态（v0.1，待 review）

本文说明基准为什么这样设计、各项设计的实现情况、需要你 review 决定的点。操作步骤见 [05-benchmark.md](05-benchmark.md)。

## 1 任务定义（基准的出发点）

- 被测接口和测试脚本都按契约实现；契约规定输入、输出和业务规则。
- 测什么、预期是什么，由人在测试剧本中决定，分为正常流和异常流。
- 模型的职责：根据剧本 + 契约 + 框架约定，忠实地写出脚本。不设计用例、不补充剧本以外的测试、不做测试因素的组合。
- 范围是业务流；系统类测试（限流、性能、稳定性、容灾）不收。

因此基准评的是**"脚本对剧本的忠实度 + 可交付性"**，不评"剧本是否充分"。后者由写剧本的人负责，所以没有故障版本（mutation testing）这一层。

## 2 要解决的问题

| 问题 | 后果 | 处理 |
| --- | --- | --- |
| 只有全局规则，没有每个任务的判定标准 | 只能看格式和框架，看不出是否实现了剧本 | 每个实例有 `oracle.json`，从剧本写出（L2.5） |
| 评测任务与训练数据在同一文件 | 数据一改基准就变，历史结果失去可比性 | 基准独立存放、冻结、带版本和 SHA |
| 只有静态检查 | 回答不了"能否跑通、是否真按剧本" | L3 执行、L4 人工评审，通过 `review.csv` 录入 |
| 任务没有标签 | 回答不了"哪类场景变好或变差" | `taxonomy.json` + 按标签切片 |
| 训练池可能混入评测任务 | 结果虚高 | `check_leakage.py` + 训练前排除检查 |

## 3 设计原则（与业内做法的对应）

1. **独立资产、冻结、版本化**：基准与训练池分开，冻结后只读，改动即新版本。HumanEval、MBPP、SWE-bench 都是固定任务集 + 固定评测脚本。
2. **每个任务自带判定标准**：类似 SWE-bench 每个实例自带验收测试；这里被测对象是"测试脚本"，所以判定写成"必须调用什么、必须断言什么、必须清理什么"，内容全部取自剧本。
3. **静态初筛 + 执行 + 人工评审**：静态判定（L0–L2.5）每次都能跑、成本低；执行（L3）确认能跑通；评审（L4）确认真的按剧本实现。
4. **分层报告，不合成单一分数**；**配对比较**：同一批任务逐任务对比。
5. **防污染**：分组隔离、精确与近重复检测；`fresh` split 借鉴 LiveCodeBench 按时间补充新题的做法。
6. **评分器自身有测试**：gold 必须通过（校准），已知坏样本必须被抓（`tests/test_bench.py`）。

## 4 实例与判定

实例目录：`task.json`、`gold.py`、`oracle.json`、`provenance.json`。字段说明见 05 第 2、4 节。

| 判定 | 规则 | 设计理由 |
| --- | --- | --- |
| `must_call` | 候选脚本调用了剧本要求的接口；自己定义同名函数再调用不算 | 防止模型"自己实现一个假接口" |
| `expect` | `full`：断言参数中有该常量且涉及 `target`；`value_only`：常量出现但不在正确对象的断言里；`miss` | 只有 `full` 算通过；`value_only` 单列，用来发现"碰巧写对数字" |
| `cleanup_required` | 清理接口出现在 tearDown（含它调用的一层 self 方法） | 资源残留会影响后续用例 |
| `must_not_call` | 不得调用 | 剧本或约定禁止的接口 |
| 校准 | gold 必须通过自己的全部判定才能冻结 | 防止判定标准写得比剧本更严 |

## 5 标签与划分

| 维度 | 取值 | 用途 |
| --- | --- | --- |
| `flow`（必填） | normal / exception | 正常流、异常流分别报告 |
| `domain`（必填） | 各业务领域 | 哪类业务改善或退步 |
| `scenario_type` | param_validation / limit / state / idempotent / cleanup / format / other | 场景分类 |
| `difficulty` | easy / medium / hard | 按前置步骤、接口、断言数量分层 |
| `api_novelty` | seen / unseen | 接口是否在训练池出现过，区分记忆与泛化 |
| `length_bucket` | <4k / 4k-8k / >8k | 长上下文的影响 |

| split | 作用 | v0.x 是否使用 |
| --- | --- | --- |
| dev | 迭代、选配置 | 是（全部实例） |
| test | 定稿后判断，每个方案只跑一次 | 否，规模扩大后再拆 |
| holdout_domain | 整个领域不进训练池，检验迁移 | 否 |
| fresh | 训练之后新写的脚本，检验时效和污染 | 否 |

规模：v0.1 为 12–16 个实例，只做逐任务案例分析，不解读比例。v1.0 目标 60–100 个实例、至少 5 个领域。test 只有 50 个实例时，两种方案通过率要相差约 15–20 个百分点以上才较可能区分开。

## 6 治理

- v0.x 试用期任何改动都发布下一个 v0.x；v1.0 起，增删实例、改 oracle 或规则 → 次版本，改输入构造或任务定义 → 主版本。
- `compare.py` 拒绝 manifest、规则或评分器版本不同的运行。评分器逻辑变化时递增 `SCORER_VERSION`（当前 0.1），旧运行重新打分写入新的 `scores/` 目录。
- oracle 目前由出题人自审，作为已知限制记录在版本说明中。
- 新发现的错误模式补进 `tests/test_bench.py`。
