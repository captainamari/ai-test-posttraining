# 04｜数据、评测与故障归因：训练数据是怎样变成证据的

## 1. 数据不能只按“条数”讨论

当前训练数据由存量脚本重建，`inputs` 五段是 `rules/scenario/api/framework/reference`，`target` 是完整 Python 文件。训练只使用 `split=train` 且审核通过的样本。实际训练文件在 `data/private/train/`，不在公开仓库内。

每个训练批次先回答：
1. **数量**：多少行、多少独立 `source_group`？
2. **覆盖**：领域、正常/异常流、场景类型、涉及 API 数量如何分布？
3. **信息充分**：目标里的每个关键 API、参数、断言都能从输入找到依据吗？
4. **一致性**：相近剧本是否对应互相矛盾的 target？
5. **冗余**：参考脚本和目标是否近重复？是否大量模板只换 ID？
6. **长度**：prompt / supervised token 各是多少？哪些样本接近 8192？
7. **泄漏**：是否跨 train/dev source_group，是否照搬 benchmark gold？

`audit_data.py` 和 `check_leakage.py` 能提供部分结构/指纹检查；**通过不等于业务语义正确**。若审核的是参考脚本重建样本，必须人工确认剧本中的预期和 target 断言一致。

## 2. Benchmark 分层如何理解

| 层 | 问题 | 局限 |
|---|---|---|
| L0 | 输出是否完整、无围栏、语法正确？ | 围栏/截断可令完整通过归零 |
| L1 | 是否符合公司测试框架约定？ | 静态代码结构不等于能运行 |
| L2 | 是否照抄参考身份、虚构输入之外的 API？ | 静态名字匹配有局限 |
| L2.5 | API、断言常量、清理是否满足 Oracle？ | 无法完全理解变量来源、调用顺序和业务状态 |
| L3 | 内网真实环境是否执行通过？ | 环境故障需要分离 |
| L4 | 是否忠实剧本、人工修复成本多少？ | 依赖一致的人类评审标准 |

`auto_pass` 是严格的 **L0–L2.5 组合规则**，不是代码任务的唯一有意义指标。以 E001 报告为例：14 个任务两组都是 0 个自动完整通过；然而未截断、语法、API 命中、断言命中等仍可用于定位问题。样本量小，差 1–2 个任务不应视为稳定结论。

## 3. 三种失败与三种证据

- **形式失败**：围栏、截断、语法错误。可先用原始输出与抽取后代码双视角诊断，但原始交付标准仍保留。
- **语义失败**：API 用错、请求条件错、断言不符合剧本、前置/清理不足。静态规则只能初筛，最终需 L3/L4 验证。
- **评测局限**：例如 Oracle 以 AST 源码字符串查找断言 target，遇到别名变量可能漏判。这应记录为“待人工核实”，不能直接宣称脚本业务错误。

输出报告至少同时保留：
- 生成是否触顶 token 限制；
- L0/L1/L2/L2.5 各自计数；
- 与同一任务 B0 的成对变化；
- 原始代码、失败原因和一次简短的人工判读；
- 如可执行，记录 run_status 与 repair_minutes。

## 4. 实验设计：隔离变量，而不是碰运气

| 研究问题 | 控制组 | 实验组 | 固定条件 | 主要看什么 |
|---|---|---|---|---|
| 训练量影响 | steps=30 | steps=112 | 模型、数据、rank、基础 LR、提示、基准 | loss + paired errors；注意 LR scheduler 随 max_steps 变 |
| 学习率影响 | LR=1e-4 | LR=5e-5 | 步数、数据、batch、目标模块 | loss/grad_norm/业务层错误 |
| rank 影响 | r=8 | r=16 | 其他配置不变 | trainable params、时间、错误结构 |
| 有效 batch 影响 | g=1 | g=4 | 尽量控制总曝光与数据 | 平滑性、updates、时间；不是完全等价 |
| 数据规模影响 | 25% 家族 | 50% / 100% 家族 | 模型、epoch、评测 | 学习曲线；按 group 抽样 |
| 生成长度影响 | 2048 | 4096 | 同一权重、同一提示 | 截断与正确任务数 |
| 输入中 reference 影响 | 原输入 | 无参考版输入 | 模型、任务、其他输入字段 | 复制身份、API/断言；属于提示消融 |

做不到严格控制时，不要写“仅 X 导致提升”；如 steps 改变线性衰减计划，也属于共同变化因素。

## 5. 如何为下一轮提出有用的假设

以观测 → 假设 → 排他测试 → 结论形式记录：

**例：**
- 观测：112 steps 相比 30 steps，train loss 下降，但复制参考脚本身份的任务更多。
- 候选解释：target/reference 近重复、训练轮数带来记忆、仅随机波动。
- 排他验证：先审计训练样本 reference/target 重合；固定生成条件并逐任务比较；不要立即同时改 rank、LR 和数据。
- 可下结论：仅当足够证据支持时，写“与……一致”，而非断言因果。

## 6. 本阶段的完成标准

- 能读懂 config / metrics / status / token-lengths / parameters 五类运行记录；
- 能计算 step ↔ epoch 的近似换算并指出限制；
- 能解释 `max_steps` 与 `learning_rate` 调度耦合；
- 能区分“训练信号正确”“模型学到格式”“脚本业务可用”三个命题；
- 能写出一次 **只有一个主实验变量** 的研究计划、事前预测和事后证据。
