# 基准人工评审标准（L4）

版本 v0.1。用法：复制到 `data/private/benchmark/rubric.md`，补充本团队的正反示例。每个评审人评审前读一遍；标准修改后在文末"修订记录"写日期，并说明它影响哪些已有评审。

评审的唯一问题是：**候选脚本是否忠实实现了该实例的测试剧本**（在契约和框架约定之下）。剧本没有要求的测试不加分，也不要求模型补充。

评审结果填在每个运行目录的 `review.csv`，一个实例一行。评审时只看候选文件和该实例的 `task.json`、`oracle.json`；不要先看模型名称或组别（A / B0 / B1），以免先入为主。

## 字段与取值

| 列 | 取值 | 判定要点 |
| --- | --- | --- |
| `executed` | yes / no | 是否在内网执行环境实际运行过（L3） |
| `run_status` | pass / fail / env_error / not_run | 在被测环境中，脚本是否按剧本跑通。正常流"跑通"指业务成功且断言通过；异常流"跑通"指接口按剧本返回了约定的错误码和文案，断言通过 |
| `environment_error` | yes / no | 账号池、网络、依赖、超时、环境限流等与脚本无关的失败。修复环境后重跑，保留原记录；不计为通过，也不从分母删除 |
| `review_verdict` | accept / minor_fix / major_fix / reject | 见下表 |
| `follows_scenario` | yes / no | 前置、动作、断言、清理是否都与剧本一致：前置按剧本构造，调用剧本要求的接口，断言了剧本写明的全部预期，没有改动剧本的意图 |
| `invented_api` | yes / no | 是否调用了输入中没有的接口、参数，或编造了返回字段 |
| `repair_minutes` | 数字 | 把它改到可交付所用的分钟数；accept 填 0 |
| `notes` | 文本 | 主要问题，用错误分类开头，便于统计 |

## review_verdict

| 取值 | 含义 | 例子 |
| --- | --- | --- |
| accept | 不改即可交付 | 前置、动作、断言、清理都与剧本一致 |
| minor_fix | 改动不涉及业务判断，10 分钟内 | 去掉 Markdown 围栏、补断言消息、修导入 |
| major_fix | 需要业务判断或重写部分逻辑 | 前置与剧本不符导致请求被其他规则先拒绝；漏了剧本写明的某个预期；断言了错误的错误码；漏清理 |
| reject | 重写比修改快 | 测的不是剧本描述的场景；照抄参考脚本；大量虚构接口 |

## 正常流与异常流

以剧本写明的预期为准：

- 正常流：剧本写了成功码和副作用（状态、余额、记录），脚本就要都断言。只断言了成功码、漏了剧本写明的副作用，视为 major_fix。
- 异常流：剧本写了错误码和文案，脚本就要都断言；前置要按剧本只违反目标规则这一条。只断言"失败"、只断言 HTTP 状态码、或漏了剧本写明的文案，视为 major_fix。

## 错误分类（写在 notes 开头）

`format`（围栏、截断、语法）、`framework`（基类、骨架、清理顺序）、`grounding`（虚构接口/参数）、`copy_reference`（照抄参考脚本身份或场景）、`precondition`（前置与剧本不符）、`assertion_missing`（漏了剧本写明的预期）、`assertion_wrong`（断言了与剧本/契约不符的预期）、`cleanup`、`other`。
